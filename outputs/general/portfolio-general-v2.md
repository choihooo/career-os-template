# General Portfolio v2

## Narrative

좋은 프론트엔드 작업은 화면을 만드는 일에서 끝나지 않습니다. 사용자가 어느 지점에서 기다리는지, 어느 순간 흐름이 끊기는지, 팀이 어떤 변경을 반복하는지까지 봐야 합니다. 제 작업은 그 지점을 타입, 상태관리, 성능, 컴포넌트 API, 자동화로 줄이는 방향에 집중되어 있습니다.

## Signature Strengths

### 1. 운영 리스크를 코드 구조와 자동화로 줄입니다

- TypeScript v3에서 v5로 단계 전환하며 50개 이상의 `any`를 명시 타입으로 바꿨습니다.
- i18n 키 누락을 CI에서 차단하는 검증 스크립트를 만들었습니다.
- 센터 데이터를 하드코딩에서 API 기반 동적 로딩으로 바꾸고 38개 파일의 참조를 제거했습니다.

### 2. 사용자가 체감하는 흐름을 기술 선택의 기준으로 둡니다

- 거부기린에서는 팝업보다 덜 방해되는 always-on-top 위젯을 중심 UX로 선택했습니다.
- 수상한 녀석들에서는 진입 전 인증 검사와 URL 동기화 폼으로 화면 튐과 상태 유실을 줄였습니다.
- 초기 번들 65% 감소처럼 사용자 대기 시간을 줄이는 최적화를 함께 진행했습니다.

### 3. 반복되는 구현 비용을 API와 검증 흐름으로 흡수합니다

- 대피로 디자인 시스템에서 Compound Component API로 레이아웃 변형 요구를 표준화했습니다.
- ESM/CJS 듀얼 빌드와 타입 정의 자동 생성으로 여러 프로젝트 환경에서 사용할 수 있는 라이브러리 구조를 만들었습니다.
- Vitest와 Storybook Test Runner를 CI에 연결해 컴포넌트 변경을 자동 검증했습니다.

## Project Stories

### Story 1. 아이겐코리아: 운영 어드민의 기술 부채를 낮춘 경험

아이겐코리아 어드민은 TypeScript 버전이 오래되어 최신 라이브러리 적용 시 충돌이 있었고, strict 모드가 꺼져 타입 안정성도 낮았습니다. 한 번에 바꾸면 오류가 크게 늘어날 수 있어 `noImplicitAny`, `strictNullChecks`, 외부 라이브러리 호환성 점검, `strict: true` 순으로 전환했습니다.

결과적으로 50개 이상의 `any`를 명시 타입으로 바꿨고, 빌드 시간은 평균 246.22초에서 199.51초로 약 19% 줄었습니다. 이 경험은 제가 기술 부채를 “크게 갈아엎는 일”보다 “서비스를 유지하며 위험을 낮추는 일”로 접근한다는 점을 보여줍니다.

### Story 2. 거부기린: 방해하지 않는 자세 교정 UX

거부기린은 자세가 무너졌을 때 바로 알려야 하지만, 팝업이 잦으면 사용자의 작업을 방해하는 문제가 있었습니다. 그래서 알림 자체보다 “어떻게 덜 방해하면서 인지시킬 것인가”를 먼저 봤습니다.

프론트엔드에서는 always-on-top 위젯을 상시 피드백 채널로 두고, 일정 시간 이상 자세가 무너진 경우에만 시스템 알림이 발생하도록 했습니다. 자세, 카메라, 알림 상태는 Zustand 도메인 store로 나눠 실시간 업데이트의 영향을 줄였습니다. 초기 번들도 1.79MB에서 0.63MB로 줄여 첫 진입 경험을 개선했습니다.

### Story 3. 대피로 디자인 시스템: 반복 요구를 줄이는 컴포넌트 API

대피로에서는 UI 변형 요구가 잦아 매번 구현 시간이 반복적으로 들었습니다. 단순히 컴포넌트를 더 만드는 대신, 변형을 조합할 수 있는 API가 필요했습니다.

Compound Component와 Context 기반 API로 컴포넌트 조합을 열고, Connect/Recipe 아키텍처로 스타일과 구조의 변경 영향을 줄였습니다. tsup, Vanilla Extract, Vitest, Storybook Test Runner, GitHub Actions를 연결해 배포와 검증 흐름도 함께 만들었습니다. 이 구조로 요구사항 대응 시간이 1-2시간에서 5-10분으로 줄었습니다.

### Story 4. 수상한 녀석들: 작성 흐름을 끊지 않는 폼 설계

작성형 서비스에서는 사용자가 뒤로가기를 누르거나 새로고침을 해도 흐름이 망가지지 않아야 합니다. 수상한 녀석들에서는 인증 확인 타이밍과 멀티스텝 폼 상태 유실이 사용 흐름을 깨는 지점이었습니다.

AuthGuard와 `useAuth`로 라우트 진입 전 인증을 확인했고, `@use-funnel/browser`와 Zod 단계별 검증으로 단계 상태를 URL과 동기화했습니다. 약 100명 대상 운영에서 62명에게 사용 흐름이 직관적이고 작성하기 편하다는 정성 피드백을 확보했습니다.
