# Example Product Frontend Portfolio

## Positioning

이 포트폴리오는 Example Product JD가 요구하는 업무용 UI, 상태 설계, 입력 검증 경험을 보여주기 위해 구성했다. 첫 번째 사례는 운영자 대시보드의 상태 흐름을, 두 번째 사례는 폼 검증과 타입 안정성을 강조한다.

## Case Study 1. Sample Dashboard

### Problem

내부 운영자는 여러 CSV를 수동으로 합쳐 주간 지표를 확인했다. 필터 조건을 공유하기 어렵고, 같은 조건으로 다시 확인하는 과정도 반복적이었다.

### Decision

서버에서 받아오는 데이터 상태와 사용자가 조작하는 필터 상태를 분리했다. 필터 조건은 URL query에 동기화해 다른 사람에게 같은 화면 상태를 공유할 수 있게 했다.

### Action

- TanStack Query로 서버 상태, 로딩 상태, 재요청 흐름을 관리했다.
- URL query에 필터 조건을 동기화해 새로고침과 링크 공유 후에도 같은 조건이 유지되게 했다.
- Recharts로 주요 지표와 추세를 시각화했다.
- 데스크톱 우선 사용 환경에 맞춰 테이블, 필터, 차트를 한 화면에서 비교할 수 있게 배치했다.

### Result

운영자로부터 주간 리포트 작성 시간이 2시간에서 30분으로 줄었다는 피드백을 받았다. 필터 조건 공유와 재현도 쉬워졌다는 정성 피드백이 있었다.

### Why This Matches The JD

이 사례는 JD의 대시보드 UI, API 연동 구조, 서버 상태 관리, 운영자 흐름 개선 요구와 직접 연결된다.

### Proof To Replace

- 실제 GitHub repository
- 대시보드 스크린샷
- 운영자 피드백 원문
- before/after 측정 방식

## Case Study 2. Sample Company Form Validation

### Problem

폼 데이터 타입이 느슨해 런타임 오류가 QA 단계에서 반복 발견됐다. 사용자가 어떤 입력을 잘못했는지 화면에서 바로 알기 어려웠다.

### Decision

입력 단계에서 오류를 차단하도록 폼 스키마와 API 응답 타입을 정리했다. 검증 실패는 명시적인 에러 메시지로 매핑했다.

### Action

- Zod 스키마를 추가해 입력 데이터의 구조와 검증 기준을 명시했다.
- API 응답 타입을 정리해 화면 상태와 서버 응답 간 불일치를 줄였다.
- 검증 실패 메시지를 사용자 입력 흐름에 맞게 매핑했다.

### Result

QA 재현 이슈 5건 중 4건이 사전 검증 단계에서 차단됐다.

### Why This Matches The JD

이 사례는 JD의 폼 입력 검증, TypeScript 기반 코드 품질 개선, QA 이슈 재현과 차단 요구에 맞다.
