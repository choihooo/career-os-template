Architecture Document

Career OS 4-Layer 설계 문서

CLI나 앱이 아니라, LLM이 문서를 읽고 따라가는 Career OS를 만들기 위한 레이어·폴더·스킬·품질 기준 설계안.

문서형 LLM Workflow Source → Knowledge → Output Workflow-controlled v0.2

1. 목적

Career OS는 사용자의 경력 자료를 모아 범용 이력서와 JD 맞춤 이력서로 재조합하는 문서형 시스템이다. 이 설계의 목표는 LLM이 자료를 헷갈리지 않고 안전하게 승격시키는 구조를 만드는 것이다.

핵심 한 줄

Career OS는 “파일 구조”가 아니라, raw의 원천을 wiki의 지식으로 정리하고 outputs의 산출물로 조립하는 문서형 운영체계다.

이 시스템은 터미널에서 career-ingest 같은 명령어를 실행하는 CLI가 아니다. career-* 이름은 LLM 에이전트가 따라야 하는 skills/ 아래의 작업 절차를 뜻한다.

2. 설계 원칙

  1. 레이어는 4개로 유지한다. 8개 이상으로 나누면 정확하긴 하지만 운영자가 매번 분류를 고민하게 된다.
  2. Source는 원천을 보존한다. 예쁜 문장보다 검증 가능성이 중요하다.
  3. Knowledge는 재사용 가능해야 한다. 이력서와 면접 답변에서 다시 쓸 수 있는 단위로 정리한다.
  4. Workflow는 데이터가 아니다. LLM의 작업 순서, 수정 권한, 품질 기준만 담당한다.
  5. Output은 Source를 대체하지 않는다. 최종 이력서가 원천 증거가 되면 안 된다.
  6. 샘플은 별도 레포에서 관리한다. 본 레포에는 실제 운영 구조만 두고, 데모 데이터와 예제 output은 별도 sample repository로 분리한다.
Decision

물리 폴더명을 01_raw, 02_wiki처럼 바꾸지 않는다. 기존의 raw/, wiki/, outputs/를 유지하고, 문서에서 개념 레이어를 명확히 정의한다.

3. 4개 레이어

Layer담당질문대표 위치
Source원천과 증거 보관이 주장의 원본 근거가 어디 있음?raw/
Knowledge커리어 지식과 주장 관리이 자료를 어떻게 재사용할 수 있음?wiki/
WorkflowLLM 작업 규칙어떤 순서로 뭘 읽고 어디까지 수정함?AGENTS.md, skills/, index.md, log.md
Output제출/공개 산출물이 결과물을 누구에게 보여줄 수 있음?outputs/, templates/, docs/

3.1 Source Layer

Source는 아직 해석되지 않은 원천 자료다. 프로젝트 메모, 경력 사실, JD 원문, PR 분석, 피드백, 수치 근거 등이 들어간다.

Do

  • 원문과 맥락을 보존한다.
  • 근거 강도를 표시한다.
  • 애매하면 raw/inbox/에 둔다.

Do not

  • 최종 이력서 문장을 저장하지 않는다.
  • 근거 없는 수치를 만들지 않는다.
  • 샘플 데이터를 넣지 않는다.

3.2 Knowledge Layer

Knowledge는 Source를 기반으로 정리된 커리어 지식이다. 프로젝트 페이지, 경험 페이지, story bank, sentence bank, claims ledger, proof map이 여기에 들어간다.

Do

  • Source와 연결된 claim을 만든다.
  • JD별로 재사용 가능한 bullet/story를 정리한다.
  • 근거 부족은 Gaps로 남긴다.

Do not

  • raw 원문 덤프를 그대로 복사하지 않는다.
  • 회사별 최종 산출물을 저장하지 않는다.
  • 출처 없는 claim을 강한 주장으로 승격하지 않는다.

3.3 Workflow Layer

Workflow는 LLM이 어떻게 일해야 하는지 정한다. 이 레이어는 데이터 저장소가 아니라 운영 규칙이다.

Do

  • mandatory read order를 정의한다.
  • allowed edits / forbidden edits를 명시한다.
  • quality gates와 log format을 정한다.

Do not

  • 실제 경력 자료를 넣지 않는다.
  • 최종 이력서 본문을 넣지 않는다.
  • “알아서 적당히” 같은 절차를 만들지 않는다.

3.4 Output Layer

Output은 제출하거나 공개할 수 있는 산출물이다. 범용 이력서, 회사별 맞춤 패키지, 최종 HTML/PDF, 공개 가이드가 들어간다. 샘플 데모는 별도 sample repository에서 관리한다.

Do

  • Knowledge를 목적에 맞게 조립한다.
  • source와 final을 구분한다.
  • 제출 전 traceability를 확인한다.

Do not

  • raw 자료의 유일한 보관 위치가 되지 않는다.
  • proof 없는 claim을 넣지 않는다.
  • 샘플 output을 본 레포의 실제 output과 섞지 않는다.

4. 레이어 이동 모델

Career OS의 기본 흐름은 아래와 같다.

External input
  ↓
Source Layer        raw/
  ↓
Knowledge Layer     wiki/
  ↓
Output Layer        outputs/

Workflow Layer      AGENTS.md, skills/, index.md, log.md
  └─ 위 이동의 규칙, 권한, 품질 기준을 관리

중요한 점은 Workflow가 별도의 데이터 흐름 위에 있는 것이 아니라, 레이어 간 이동을 통제하는 운영 레이어라는 점이다.

6. 복합 프로젝트 처리 방식

거부기린처럼 하나의 프로젝트가 U300, CMK 창업경진대회, KUSITMS 활동 등 여러 맥락에 걸칠 수 있다. 이때 원칙은 다음과 같다.

Rule

Source에서는 이벤트/증빙 단위로 분리하고, Knowledge에서 프로젝트 중심으로 통합한다.

6.1 거부기린 예시

project:posture-turtle
├── raw/projects/posture-turtle.md
├── raw/activities/2024-kusitms-32-posture-turtle.md
├── raw/awards/2026-u300-selection.md
├── raw/awards/2026-cmk-startup-competition.md
├── raw/evidence/github/posture-turtle-github-analysis.md
└── raw/assets/projects/posture-turtle/

Knowledge hub:
└── wiki/projects/posture-turtle.md

6.2 왜 나누는가?

같은 거부기린이라도 출력 목적에 따라 강조점이 달라진다.

목적강조할 내용주로 참조할 source
Frontend 지원Tauri/React UI, 데스크톱 UX, 상태/설정 관리raw/projects/posture-turtle.md, GitHub evidence
FDE/AX 지원AI 분석 흐름, 사용자 문제 정의, 데이터 흐름project source, technical decision notes
스타트업/제품 직무문제 검증, U300/CMK 외부 인정, 사업화 가능성raw/awards/, raw/activities/
협업 경험KUSITMS 팀 프로젝트, 역할 분담, MVP 개발raw/activities/2024-kusitms-32-posture-turtle.md

6.3 Award냐 Activity냐

상황위치예시
수상/선정/합격/인증 결과가 있음raw/awards/U300 선정, CMK 수상, Hanyang startup club 선정
참가/발표/멘토링/프로그램 수행이 중심raw/activities/CMK 경진대회 참가, 창업 멘토링 참여
둘 다 중요함둘 다 생성참가 과정은 activities, 수상 결과는 awards

7. Source 메타데이터

모든 raw markdown 파일은 최소 frontmatter를 가진다. 이것은 나중에 Knowledge 승격과 lint의 기준이 된다.

---
type: project
id: project:posture-turtle
title: 거부기린 / Posture Turtle
status: draft
 evidence_strength: medium
created_at: 2026-06-22
updated_at: 2026-06-22
related:
  experiences: []
  activities:
    - activity:kusitms-32-posture-turtle
  awards:
    - award:u300-selection
    - award:cmk-startup-competition
  evidence:
    - evidence:github-posture-turtle
---

7.1 필드 정의

필드의미값 예시
typesource 종류profile, experience, project, activity, award, application, evidence, inbox
id다른 문서가 참조하는 안정 IDproject:posture-turtle
status검증/정리 상태draft, verified, needs-proof, deprecated
evidence_strength근거 강도high, medium, low, unknown
related연결 source IDactivities, awards, evidence 등
주의: Source의 evidence_strength는 “이 자료가 얼마나 강한 원천인가”를 뜻한다. 이력서에 바로 써도 된다는 뜻이 아니다. 최종 claim 승격은 Knowledge에서 한다.

8.1 claims-ledger

wiki/claims-ledger.md는 이력서와 면접 답변에 사용할 수 있는 주장을 관리한다.

## claim:posture-turtle-u300-validation

- Claim: 거부기린은 U300 선정으로 초기 사업화 가능성을 외부 검증받았다.
- Allowed use: resume | interview
- Source pages:
  - raw/awards/2026-u300-selection.md
  - raw/projects/posture-turtle.md
- Proof IDs:
  - proof:u300-selection
- Confidence: high
- Caveat: 선정의 정확한 명칭과 연도는 증빙 기준으로 표기한다.

8.2 proof-map

wiki/proof-map.md는 어떤 증빙이 어떤 claim을 뒷받침하는지 연결한다.

## proof:u300-selection

- Type: selection
- Source: raw/awards/2026-u300-selection.md
- Related item: project:posture-turtle
- Evidence strength: high
- Notes: 선정 메일/공고/이미지 확인 필요.

Decision

본 레포는 실제 사용자 자료가 들어갈 운영 구조만 제공한다. 샘플 데이터, 가짜 이력서, 예제 output, walkthrough는 별도 sample repository에서 관리한다.

11. 스킬 구성

스킬은 레이어 전환 단위로 둔다. 사용자-facing skill은 6개면 충분하다.

12. 품질 기준

12.1 Source 품질 기준

  • 모든 raw 파일은 type, id, status, evidence_strength를 가진다.
  • 근거가 약하면 needs-proof 또는 low로 표시한다.
  • 분류가 애매하면 raw/inbox/에 임시 저장한다.

12.2 Knowledge 품질 기준

  • 강한 claim은 source/proof로 역추적 가능해야 한다.
  • 프로젝트 hub 페이지는 related source map을 가진다.
  • 출처 없는 문장은 final output으로 가지 않는다.

12.3 Workflow 품질 기준

  • 모든 skill은 allowed edits와 forbidden edits를 명시한다.
  • 모든 workflow는 마지막에 log.md를 append한다.
  • career-lint는 기본적으로 read-only다.

12.4 Output 품질 기준

  • 제출용 output에는 샘플 데이터가 없어야 한다.
  • JD 맞춤 패키지는 brief.md에 강조점과 gaps를 남긴다.
  • final HTML/PDF는 source markdown을 대체하지 않는다.

13. 유스케이스 흐름

아래 유스케이스는 사용자가 실제로 Career OS를 쓰는 대표 시나리오다. 각 흐름은 어떤 스킬을 쓰고, 어느 레이어를 건드리는지 기준으로 정리한다.

UC-01. 새 raw 자료를 등록하고 지식으로 정리하기

사용자가 프로젝트 메모, 수상 기록, 활동 기록, 피드백 같은 자료를 직접 입력했을 때의 기본 흐름이다.

Skillcos-register-sourceraw 위치 결정, ID/frontmatter 부여
Sourceraw/** 등록원천 보존, evidence strength 표시
Skillcos-ingestsource를 읽고 지식화
Knowledgewiki/** 갱신프로젝트/경험/claim/proof 정리
필수 여부필수 core flow최종 산출raw/**, wiki/**, log.md

UC-02. GitHub 레포를 경력 증거로 보강하기

개발 프로젝트의 실제 기여, PR, commit, 변경 파일, 기술 의사결정을 source evidence로 만들 때 사용한다.

필수 여부선택. 개발자 이력서에는 권장주의레포 전체 성과와 사용자 본인 기여를 분리한다.

UC-03. 복합 프로젝트를 프로젝트 hub로 통합하기

거부기린처럼 프로젝트 본체, U300 선정, CMK 경진대회, KUSITMS 활동이 한 프로젝트에 연결되는 경우다.

UC-07. 전체 상태 점검하기

자료를 많이 넣었거나 output을 만들기 전후에 전체 구조와 근거를 확인한다.

Skillcos-lintread-only diagnostic report
필수 여부필수 quality gate기본 정책read-only. 수정은 사용자가 명시 요청할 때만 한다.

14. 적용 순서

  1. README.md에 “문서형 LLM workflow”임을 명시한다.
  2. AGENTS.md에 mandatory read order와 layer rules를 추가한다.
  3. LAYER_CONTRACT.md 또는 본 문서의 내용을 repo 문서로 추가한다.
  4. raw/README.md, wiki/README.md, outputs/README.md를 만든다.
  5. 실제 운영 파일에서 샘플 오염을 제거하고, 데모 데이터는 별도 sample repository로 이동한다.
  6. wiki/claims-ledger.md와 wiki/proof-map.md를 추가한다.
  7. career-capture-source 스킬을 추가한다.
  8. 기존 스킬 5개를 표준 섹션 구조로 정리한다.
  9. index.md를 운영 지도처럼 재작성한다.
  10. log.md에 새 log format 정책을 추가한다.

16. 현재 스킬 규칙 점검

현재 career-os-template 레포의 skills/*/SKILL.md를 새 설계 기준으로 점검한 결과다. 결론은 “좋은 안전 규칙은 유지하되, portfolio/samples/career-* 중심의 오래된 규칙을 resume-only/cos-* 기준으로 정리해야 한다”이다.

핵심 결론

현재 스킬은 “커리어 위키 + 이력서/포트폴리오 패키지” 기준이고, 새 설계는 “resume-only Career OS + 별도 sample repo + claim/proof 중심” 기준이다. 따라서 output, portfolio, samples, naming, allowed edits 규칙을 대폭 정리해야 한다.

16.1 유지할 좋은 규칙

Keep

공통 read order

  • AGENTS.md, index.md, log.md를 먼저 읽는 규칙은 유지한다.
  • 작업 전 기존 wiki/, outputs/를 읽어 중복 생성을 막는다.
Keep

근거 없는 주장 금지

  • metric/date/impact를 invent하지 않는 규칙은 모든 스킬에 유지한다.
  • evidence missing은 추측하지 말고 Gaps로 남긴다.
Keep

GitHub ownership 분리

  • repo만 보고 본인 기여를 추정하지 않는다.
  • commit/PR/file evidence와 interpretation을 분리한다.
Keep

lint read-only 원칙

  • career-lint의 기본 read-only 정책은 cos-lint에서도 유지한다.
  • 수정은 사용자가 같은 턴에 명시적으로 요청한 경우에만 한다.
